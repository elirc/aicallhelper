evidence: src-tauri/core/src/session/machine.rs:307 `deps.llm.prewarm()` immediately followed by :313 `tokio::spawn(answer task)`; warm.rs:75-97 spawns a `GET <origin>/v1/models` on `shared_client()`; http.rs:35-59 builds the client with `pool_max_idle_per_host(4)` and core/Cargo.toml reqwest features are only `rustls-tls, stream, json` (no `http2`), so every connection is HTTP/1.1 and serves one request at a time; anthropic.rs:122 / groq.rs:85 send the POST through the same client. Both tasks are spawned back-to-back onto the same tokio worker (LIFO slot vs local queue), so which one checks out the idle connection left by the previous session is nondeterministic. The same collision exists on Stop (machine.rs:265, :570) whenever the STT finalize resolves faster than the warm GET round-trip (e.g. stream already dead -> finalize returns instantly).
problem: On a typed question the warm cannot overlap anything: if the pool is empty both GET and POST open cold connections (wasted socket, zero gain); if an idle warm connection exists the GET frequently grabs it first and the POST must either wait for the GET to round-trip or open its own cold connection, adding up to one provider RTT (~50-200 ms) to firstTokenMs. On Stop the same theft happens on fast finalizes. The 2 s throttle (warm.rs:34) does not prevent it because Ask/Stop are normally >2 s after the last warm.
proposal: Remove `deps.llm.prewarm()` from `SessionManager::ask` (machine.rs:307); keep the Record-time and Stop-time warms (those genuinely overlap recording / finalize). Update docs/SPEC.md §6.4 ('on Record press, on Ask, and on Stop press' -> drop 'on Ask'), docs/TESTING.md:223, and the pinned test `prewarm_fires_on_start_stop_and_ask` (machine.rs:2019 expects the count to reach 3 at ask). Optional second step to also remove the Stop-path collision without touching the spec: enable the reqwest `http2` feature in core/Cargo.toml so GET and POST multiplex on one connection; validate SSE streaming over h2 against both providers and measure with the latency telemetry panel (IDEAS #3) before shipping.
risk: Spec string §6.4 and test `prewarm_fires_on_start_stop_and_ask` change (count 3 -> 2 at ask). The http2 option changes wire behaviour for both providers and must be measured, not assumed.

## RS-2 [medium/S] WASAPI device open blocks a tokio worker with the just-spawned Deepgram dial parked in its non-stealable LIFO slot
files: src-tauri/src/commands.rs
evidence: src-tauri/src/commands.rs:110 `start_session` is an `async` command, so it runs on tauri's tokio multi-thread runtime. :135 `state.sessions.start(deps).await` has no internal await; inside it machine.rs:230 spawns the warm task and :233 spawns `drive_recording` (the Deepgram `connect_async`) — the last spawn lands in the current worker's LIFO slot. Keep the `state.sessions.is_active(session_id)` re-check after the await exactly as it is (it already handles supersession during the open). With this the default runtime needs no tuning (no other blocking call runs on a worker).
risk: None to spec strings. The `state.audio` mutex is taken only after the await, so no lock crosses it; the superseded-capture stop at commands.rs:142 stays before the open.

## RS-3 [medium/M] `set_settings` (and `open_external`) run on the main thread: fsync + 3x DPAPI re-encrypt + 400 KB rewrite per style-chip click

## RS-6 [low/S] Shared HTTP client has no connect timeout or TCP keepalive: a silently dropped pooled connection hangs the answer to the 10 s first-token timeout
files: src-tauri/core/src/llm/http.rs, src-tauri/core/src/llm/anthropic.rs, src-tauri/core/src/llm/groq.rs, docs/SPEC.md
evidence: src-tauri/core/src/llm/http.rs:36-59 sets `use_rustls_tls`, `pool_idle_timeout(120 s)`, `pool_max_idle_per_host(4)` and deliberately no whole-request `.timeout` (:45-49), but also no `.connect_timeout` and no `.tcp_keepalive`.
